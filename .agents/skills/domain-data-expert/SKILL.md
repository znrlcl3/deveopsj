# 금융 도메인과 데이터
1. 요청 DTO → Service → Repository/Entity와 결과를 사용하는 화면/집계를 읽는다. 공용 종목·공통코드와 개인 데이터의 소유권 범위를 구분한다.
2. 개인 데이터는 인증된 member 식별자로 조회·변경한다. goal, assetPlan 등 연관 ID도 본인 소유인지 확인한다. 클라이언트의 member 값이나 Entity 직접 바인딩을 신뢰하지 않는다.
3. 원화 정수 금액과 BigDecimal 수량·단가·환율을 구분한다. 저장 단위, 반올림 위치, overflow, null/0, 매도 가능 수량, 월말 잔액과 현금흐름의 차이를 검증한다. 실시간 평가액과 월말 원가를 혼용하지 않는다.
4. 반복 지출·납입은 설정 규칙과 실제 확정 데이터를 구분한다. 월말/윤년, 중복 확정, 규칙 변경이 이미 확정된 내역에 미치는 영향을 확인한다.
5. 공통코드는 활성 목록의 codeId 계약을 사용한다. 이름·표시값과 저장 키를 구분하고 AI fallback도 활성 목록 안에서 선택한다.
6. 저장 전체 검증과 트랜잭션 경계를 확인한다. 조회 후 중복 검사만으로 동시 실행을 막았다고 단정하지 말고 DB 제약과 충돌 처리를 함께 검토한다.
7. 저장·중복·스키마는 Entity·Repository, 로컬 deploy/sql과 프로필 구조로 검토한다. 매핑과 SQL에서 확인한 제약, 운영에 실제 적용됐는지 마스킹 자료가 필요한 제약을 구분한다. 변경 SQL은 기존 데이터 영향·적용 순서·재실행 조건과 함께 검토안으로만 제공한다. 어떤 환경에서도 ORM flush, 프로시저, 마이그레이션, 테스트 시드, 앱 호출, 롤백 시험으로 DB를 변경하지 않는다.

## 파일 가져오기·내보내기
- 분석 전에 파일의 실제 형식, 수정 시각, 계좌 구분, 조회 기간을 확인한다. 같은 경로의 파일이 교체될 수 있으므로 이전 추출물을 재사용할 때는 내용 해시를 이전 원본과 대조한다. 비교할 해시가 없으면 현재 원본을 다시 추출한다. 파일명·크기·수정 시각만으로 동일성을 확정하지 않는다. 결과에 출처와 기간을 남기되 개인정보·원본은 저장소 문서에 복사하지 않는다.
- 확장자만으로 형식을 결정하지 않는다. XLSX, 바이너리 XLS, HTML 표 형태의 XLS를 구분하고 인코딩·다중 머리글을 확인한다. 암호화/DRM 파일을 정상 표로 오인하지 않는다. 파일 분석 도구와 앱 파서 구현은 별개의 검증 대상이다.
- 거래일/결제일, 원금/평가액, 입출금/매매, 배당·이자, 세전/세후, 원화/외화를 구분한다. 한 자금 이동의 입금과 계약 매수를 이중 합산하지 않고, 원본에 없는 환율·분류는 추정임을 표시한다.
- common/excel의 기간·열·날짜·금액 계약과 spending의 기존 XLSX 가져오기 계약을 함께 확인한다. 범위 제한을 UI만으로 처리하지 않는다.
- 카드 파서는 카드사별 구조·취소/제외 행·중복 거래 키를 확인한다. 일반 XLSX 일괄 등록과 카드 미리보기/선택 확정의 저장 정책을 혼용하지 않는다.
- 크기·행 수·파일 형식·암호화 여부, 전체 검증 후 저장, 동일 파일 재등록과 동시 확정의 결과를 검증한다.
- 업로드 원본과 비밀번호를 로그/fixture에 넣지 않는다. 합성 workbook을 테스트에 사용한다. 미리보기 세션·확정 토큰·선택 행 변조는 Web 역할과 확인한다.
- 카드 분류 호출 변경은 AI 역할과 입력 최소화·활성 코드·실패 후 저장 정책을 합의한다.

구현 요청에서 계산·소유권·중복 처리는 DB 연결 없는 단위·mock 사례로 확인할 수 있다. DB 제약이 실제 동작한다고 단정하지 않는다.

## 화면 간 계산 계약
- 계산 변경 전 포함·제외 항목, 단위, 부호, 기준일과 날짜 경계의 포함 여부를 짧게 정리한다. 시작 원금과 이후 순납입, 외부 납입과 수익 재투자, 생활비 수입과 투자수익, 실제 기록과 예정·추정치를 구분한다. 합의되지 않은 분류를 조용히 확정하지 않는다.
- 대시보드·월간 자금흐름·내 자산·목표·내역·내보내기 중 영향을 받는 소비자를 나열한다. 같은 회원·기간·기준일의 합계가 일치하는지 확인하고 목적상 다른 값은 차이의 이유를 명시한다.
- 과거/현재/미래 월, 기준일 당일과 다음 날, 시작 원금에 포함된 납입, 예정 건의 실제 확정을 관련 사례로 검증한다. 예정·추정치를 조회했다는 이유로 실제 거래에 저장하지 않는다.
- '오늘'을 사용하는 계산은 업무 시간대와 JVM/서버 시간대를 확인한다. 날짜만 있는 거래일을 임의로 UTC 변환하지 않고, 한 집계의 기준 시각은 일관되게 사용한다. 관련 변경의 테스트는 Clock 또는 명시적 기준일 등으로 시각을 고정해 자정·월말 경계를 재현한다. 이 지침만으로 기존 시간대/코드를 일괄 변경하지 않는다.
