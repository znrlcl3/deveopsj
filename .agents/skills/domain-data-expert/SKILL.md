# 금융 도메인과 데이터
1. 요청 DTO → Service → Repository/Entity와 결과를 사용하는 화면/집계를 읽는다. 공용 종목·공통코드와 개인 데이터의 소유권 범위를 구분한다.
2. 개인 데이터는 인증된 member 식별자로 조회·변경한다. goal, assetPlan 등 연관 ID도 본인 소유인지 확인한다. 클라이언트의 member 값이나 Entity 직접 바인딩을 신뢰하지 않는다.
3. 원화 정수 금액과 BigDecimal 수량·단가·환율을 구분한다. 저장 단위, 반올림 위치, overflow, null/0, 매도 가능 수량, 월말 잔액과 현금흐름의 차이를 검증한다. 실시간 평가액과 월말 원가를 혼용하지 않는다.
4. 반복 지출·납입은 설정 규칙과 실제 확정 데이터를 구분한다. 월말/윤년, 중복 확정, 규칙 변경이 이미 확정된 내역에 미치는 영향을 확인한다.
5. 공통코드는 활성 목록의 codeId 계약을 사용한다. 이름·표시값과 저장 키를 구분하고 AI fallback도 활성 목록 안에서 선택한다.
6. 저장 전체 검증과 트랜잭션 경계를 확인한다. 조회 후 중복 검사만으로 동시 실행을 막았다고 단정하지 말고 DB 제약과 충돌 처리를 함께 검토한다.
7. 스키마 변경은 deploy/sql의 기존 방식과 운영 validate 설정을 고려해 기존 데이터·적용 순서·재실행 영향을 기술한다. 실제 DB 적용은 별도 실행 요청 범위에서만 한다.

## 파일 가져오기·내보내기
- common/excel의 기간·열·날짜·금액 계약과 spending의 기존 XLSX 가져오기 계약을 함께 확인한다. 범위 제한을 UI만으로 처리하지 않는다.
- 카드 파서는 카드사별 구조·취소/제외 행·중복 거래 키를 확인한다. 일반 XLSX 일괄 등록과 카드 미리보기/선택 확정의 저장 정책을 혼용하지 않는다.
- 크기·행 수·파일 형식·암호화 여부, 전체 검증 후 저장, 동일 파일 재등록과 동시 확정의 결과를 검증한다.
- 업로드 원본과 비밀번호를 로그/fixture에 넣지 않는다. 합성 workbook을 테스트에 사용한다. 미리보기 세션·확정 토큰·선택 행 변조는 Web 역할과 확인한다.
- 카드 분류 호출 변경은 AI 역할과 입력 최소화·활성 코드·실패 후 저장 정책을 합의한다.

변경된 계산·소유권·중복 처리에 맞는 기존 Service/Controller 테스트를 확장한다. DB 제약 검증은 mock만으로 증명하지 않는다.
