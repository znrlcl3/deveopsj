# 변경에 맞는 품질 검증
1. 이번 diff와 기존 사용자 변경을 구분하고 수용 기준의 실패를 잡을 검증을 선택한다. 저위험 문구·문서 수정에는 구현을 복제하는 테스트를 만들지 않는다.
2. 분석·비교 및 하네스 작업은 로컬 소스·SQL·설정과 마스킹 자료로 검토한다. 구현 요청에서 테스트를 선택할 때는 초기화, fixture, 호출 서비스와 빌드 단계까지 읽어 DB 접속·변경이 없음을 확인한 순수 단위·mock 검증만 실행 후보로 둔다.
3. 계산·저장·보안·공유 계약 변경은 영향받는 소비자와 경계 사례를 넓게 검토하되 전체 Maven 테스트를 기본 실행하지 않는다. 단순 문구·배치는 관련 템플릿·렌더링과 허용된 화면 이동 범위로 검증한다.
4. 하네스/문서만 변경하면 메타데이터, 파일 참조, 역할·스킬 연결, 정상/경계 라우팅과 규칙 충돌을 정적으로 검사한다.
5. src/test/resources/application-test.yml의 H2 설정은 JPA 초기화 시 create-drop으로 DDL을 발생시킨다. test 프로필·인메모리 DB·@Transactional 롤백은 예외가 아니다. 시드·DDL·쓰기 가능성이 있거나 대상 환경/부작용이 불명확하면 실행을 생략하고 미검증 사항을 기록한다.

## 판정과 보고
사용자가 제공한 마스킹 실패 자료는 최초 원인을 기준으로 변경 결함·기존 실패·환경 차단으로 구분한다. DB 접근·쓰기 가능성 때문에 제외한 검증은 권한을 높여 재시도하지 않는다. Mockito agent가 필요하면 현재 의존성 버전과 환경 경로에서 찾고 개인 PC 경로를 복사하지 않는다.

검증에 사용한 테스트가 Git 추적 대상인지 확인한다. ignore가 기존 추적 파일을 제외하지 않으며 신규 테스트는 로컬에만 남을 수 있다. 로컬 통과와 다른 PC에서 재현 가능한 검증을 구분하고 사용자의 테스트 제외 정책을 임의로 바꾸지 않는다.

보안 우회·데이터 손상·빌드 불능은 Critical, 기능·계약 실패는 Major, 유지보수성은 Minor로 파일과 재현 근거를 남긴다. 실제 명령, 종료 결과, 실행/실패/미실행 구분을 제공하고 테스트 개수는 보고서에서 확인한다.
자격증명·실제 금융 데이터·외부 유료 API에 의존하는 검증은 합성 데이터/stub으로 격리한다. 통과한 검증은 새 변경·실패·미해결 우려가 있을 때만 반복한다.
