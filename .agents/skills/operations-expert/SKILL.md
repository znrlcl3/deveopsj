# 빌드와 운영 설정
1. pom.xml과 wrapper, deploy/README.md, 요청 관련 deploy/·docs/·프로필만 읽는다. 로컬 application.properties나 실제 env 파일을 통째로 출력하지 않는다.
2. 현재 Java/Spring Boot/의존성 버전과 코드의 import를 기준으로 작업한다. 구버전 예제의 보안·테스트·Jackson API를 그대로 도입하지 않는다.
3. 기본/prod/keycloak/opa 프로필의 활성 조건과 조합을 확인한다. 환경변수 이름은 설정 소비자, 예제, 문서에서 맞추고 실제 값은 기록하지 않는다.
4. prod의 DB validate, 세션 쿠키/HTTPS, 프록시 전달 헤더, health 공개 범위, 로그인 정책을 함께 확인한다. Keycloak/OPA 변경은 Web 역할과 합의한다.
5. 스키마 변경은 deploy/sql 수동 SQL의 적용 순서, 기존 데이터 호환성, 잠금/백업/실패 시 복구 방안을 검토한다. 마이그레이션 프레임워크가 있다고 가정하지 않는다.
6. 설정·배포 파일 편집은 명시된 대상에 한한다. 하네스 적용으로 배포하지 않는다. 운영 DB 확인 요청은 사용자가 직접 실행할 제한된 SELECT를 작성하고 마스킹 결과를 받는 절차로 처리한다. 접근 가능 여부를 직접 시험하지 않는다.
7. Maven 패키징도 테스트·플러그인을 실행할 수 있으므로 [QA 실행 기준](../qa-engineer/SKILL.md)을 먼저 확인한다. 검증하지 않은 설정과 운영 상태는 미확인으로 표시한다.

환경 오류는 코드 실패와 구분한다. 의존성 다운로드 실패나 DB 부재 때문에 운영 보안 설정을 완화하거나 테스트를 삭제하지 않는다.
사용자별 증권 연결의 암호화 설정은 NamuhSecretCipher 등 실제 소비자를 확인한다. 키 부재 시 동작, 환경별 키 공급, 교체 시 기존 암호문 복호화·이전 계획을 검토하며 실제 키를 출력하거나 검증 목적으로 임의 교체하지 않는다. 암호화/회원 격리는 Web, 연결 API는 Market과 확인한다.

## SQL 전달과 결과 확인
- 로컬 스키마 정의·SQL과 마스킹 자료로 DB 종류, 대상 키, 회원·기간·조건을 특정한다. 키·조건이 불명확하면 필요한 정보부터 묻는다. 운영 데이터 확인용 SELECT는 필요한 열과 대상만 조회하며 잠금이나 변경을 일으키는 함수 호출을 포함하지 않는다.
- 보정 요청에는 **대상 확인 SELECT → 변경 SQL → 결과 확인 SELECT** 순서로 검토안을 제시한다. 전후 조회는 같은 대상 키와 조건으로 실제 대상 테이블을 비교하도록 작성한다. 예상 영향, 중복·재실행 조건, 원래 값이나 백업 등 복구 전제를 적는다. 실측 건수·변경 성공·복구 가능성을 추정으로 확정하지 않는다. 사용자가 준 마스킹 결과만 해석한다.
- Workbench 전달 시 변수 설정부터 검증까지 실행해야 할 범위를 명시한다. safe-update 오류는 키 조건과 대상 범위를 먼저 확인하고 전역 안전 설정 해제를 기본 해법으로 삼지 않는다. 트랜잭션이 지원되지 않는 DDL의 자동 커밋도 구분한다.
- 문서의 금지 규칙과 실행 환경의 차단을 구분한다. 운영 자격증명 미제공, DB 커넥터 비활성화, 운영망 차단은 근거가 없으면 각각 **미확인**으로 보고한다. 자격증명 값 조회나 연결 시험으로 확인하지 않는다. 명령 예제의 경로는 저장소 상대 경로나 환경에서 확인한 경로를 사용한다.
