# DeveopsJ 작업 조율

## 실행 방식
기본은 현재 에이전트가 필요한 역할 지침과 스킬만 읽어 순차 수행하는 전문가 풀 방식이다. 역할을 적용했다는 사실을 별도 에이전트를 실행했다는 뜻으로 보고하지 않는다. 모델은 세션 설정을 상속하고 특정 제품의 모델명을 강제하지 않는다.

사용자가 병렬/서브에이전트 작업을 요청하거나 적용되는 상위 지침이 명시적으로 요구할 때만 위임한다. 도구가 있다는 사실은 위임 요청이 아니다. 위임 시 실제 제공된 협업 도구를 사용하고 역할 파일, 입력, 수용 기준, 담당 파일, 수정 가능 여부를 전달한다. 같은 파일은 한 작업자만 수정하며 공유 DTO·스키마 변경을 먼저 확정한다. 각 결과의 수정 파일·검증·미완료 항목을 회수한 뒤 통합한다. 도구가 없으면 직접 순차 수행한다.

## 0. 현재 상태
- AGENTS.md, pom.xml, git 상태와 요청 관련 소스·테스트를 확인한다. 기존 변경과 이번 변경을 구분하고 사용자 작업을 덮어쓰거나 일괄 정리하지 않는다.
- 이전 작업 보완은 실제 diff·실패 결과부터 읽는다. _workspace가 있으면 관련 자료만 활용하고 없어도 만들 필요는 없다.
- 구조가 낯설거나 여러 경계를 건드리면 [프로젝트 지도](references/project-map.md)를 읽고 현재 코드와 대조한다. 지도는 스냅샷이며 기능 구현이나 검증 완료를 보장하지 않는다.

## 1. 범위와 역할 선택
작은 변경은 담당 역할과 QA 관점을 현재 에이전트가 적용한다. 여러 경계 또는 계약 변경은 project-lead 지침도 읽고 사용자 관점의 수용 기준과 생산자 → 소비자 순서를 정한다.

| 요청 범위 | 주 담당 | 필요한 협업 |
| --- | --- | --- |
| 금융 저장·계산, 수입·매매·납입·평가, 반복 규칙, 현금흐름 | domain-data-expert | 화면/인가 변경 시 web-security-expert |
| XLSX 내보내기·일괄 등록·카드 파서·중복 방지 | domain-data-expert | 업로드/세션은 web-security-expert, 분류는 ai-integration-expert |
| Controller·Thymeleaf·JS, 로컬 로그인·Keycloak, 관리자 전환, OPA/Rego | web-security-expert | 소유권 쿼리는 domain-data-expert, 프로필은 operations-expert |
| Gemini 피드백·지출 분석·카테고리 예측 | ai-integration-expert | 저장/활성 공통코드는 domain-data-expert |
| KIS 토큰·시세·환율, KRX/Nasdaq 종목 동기화 | market-integration-expert | 포트폴리오 산식은 domain-data-expert, 관리 권한은 web-security-expert |
| 포트폴리오 평가·월별 원가 | domain-data-expert | 시세/환율 계약은 market-integration-expert |
| Maven·운영 프로필·배포 설정·SQL 적용 계획 | operations-expert | 스키마는 domain-data-expert, 인증은 web-security-expert |
| 코드 리뷰·테스트·빌드 실패 | qa-engineer | 실패 경계의 담당 역할 |

각 이름은 .agents/roles/{name}.md와 .agents/skills/{name}/SKILL.md에 대응한다.

## 2. 구현과 인수인계
- 금융 데이터 조회·변경·내보내기는 인증 사용자 소유권으로 제한한다. 공용 종목/공통코드와 개인 거래 데이터를 구분한다.
- 입력 DTO, 서버가 정하는 사용자 식별자, 활성 공통코드 계약을 유지한다. 금액 단위·반올림·날짜 경계·중복 처리 기준은 구현 전에 확인한다.
- 외부 호출은 장애 의미에 맞춰 처리한다. AI/시세 대체 결과와 OPA의 장애 시 거부를 혼동하지 않는다. 모든 연동을 하나의 공통 fallback으로 묶지 않는다.
- 담당 결과에는 변경 이유, 파일, 입출력 계약, 데이터/설정 영향, 실행한 검증과 미검증을 남긴다. 작은 작업에는 채팅 요약만으로 충분하다.
- SQL 파일 작성과 실제 DB 적용, 배포 파일 수정과 실제 배포를 구분한다. 실행 요청이 없는 운영 변경은 준비까지만 한다.

## 3. 검증 게이트
[QA 스킬](../qa-engineer/SKILL.md)에 따라 변경에 가까운 검증부터 실행한다. 문서·하네스만 바꿨다면 참조·라우팅·규칙 모순 검증으로 마친다. 애플리케이션 코드/설정은 관련 테스트 후 전체 Maven 테스트를 기본으로 하되, 환경 차단이나 명확한 범위 제외는 이유를 기록한다.

소유권/권한 우회, 데이터 손상, 변경으로 인한 빌드·테스트 실패, 계약 불일치는 미해결 완료로 보고하지 않는다. 외부 DB나 도구가 없어 실행 못 한 검증은 통과로 표시하지 않는다. 새 변경이나 실패가 없으면 통과한 검증을 반복하지 않는다.

## 4. 오류와 보고
재시도 가능한 일시 오류만 원인을 확인한 뒤 한 번 재시도한다. 인증·권한·사용량 제한은 같은 호출을 반복하지 않는다. 환경 제한과 코드 결함을 구분하며 사용자 설정을 임의로 완화하지 않는다.
최종 보고는 무엇이 달라졌는지, 검증 결과, 미검증과 남은 영향을 담는다. 하네스 구조 변경 시 AGENTS.md 이력을 갱신한다.

## 커밋 안내
- "내가 커밋할까?", "커밋할까?", 커밋 메시지 요청에는 Git 명령이나 스테이징 없이 이미 알려진 변경 맥락으로 제목과 필요한 본문만 제공한다.
- "커밋해줘", "네가 커밋해"처럼 실행을 명시한 경우에만 관련 변경 범위를 확인하고 커밋한다. 기존 사용자 변경을 자동으로 모두 포함하지 않는다.

## 테스트 시나리오
- 정상: 카드 업로드 수정 → Domain이 파서/중복 규칙, Web이 미리보기 세션/CSRF, AI 변경이 있으면 AI가 분류 계약을 확인하고 QA가 재등록·타인 접근을 검증한다.
- 장애: 시세·환율 timeout → Market이 캐시 상태를 확인하고 Domain/Web이 미조회와 대체 환율 표시를 검증한다.
- 보안: OPA timeout → Web이 요청 거부와 소유권 조건 유지를 검증한다.
- 환경: MySQL 없는 전체 테스트 실패 → QA가 실패 원인·실행된 테스트를 보고한다. 성공으로 포장하거나 운영 보안을 풀지 않는다.
- 후속: "방금 고친 환율 표시만 다시" → 기존 diff에서 해당 계약과 화면만 재검증한다.
- 경계: "내가 커밋할까?" → Git 실행 없이 메시지 안내로 끝낸다.

하네스 변경 시 [라우팅 검증 사례](references/routing-checks.md)로 정상·경계 요청과 실패 흐름을 점검한다.
